# 🚨 DIRECTIVA ARQUITECTÓNICA DE UI: React Native + NativeWind (Específico para Android)

Por favor, memoriza y aplica estas 3 reglas estrictas de renderizado para todo futuro componente de UI que construyas en este proyecto. Tuvimos un bug crítico donde el motor de Android colapsaba y cortaba la pantalla horizontalmente por no seguir estas pautas:

1. REGLA DE SOMBRAS Y BORDES (El bug principal): 
NUNCA utilices la clase `overflow-hidden` combinada con utilidades de sombra (ej. `shadow-sm`) y bordes redondeados (`rounded-2xl`) en contenedores o tarjetas (<View>). En Android, esta combinación provoca que el layout colapse y el contenido interno desaparezca o se corte de forma plana. Si necesitas sombras y bordes, elimina siempre el `overflow-hidden` a menos que sea estrictamente necesario para recortar una imagen.

2. REGLA DEL SAFEAREAVIEW:
Cuando utilices `SafeAreaView` de `react-native-safe-area-context`, EVITA usar NativeWind para asignarle flexión (`className="flex-1"`). El motor a veces falla al calcular su altura total. En su lugar, utiliza siempre estilos en línea para la estructura principal: `style={{ flex: 1, backgroundColor: '...' }}`.

3. REGLA DEL SCROLLVIEW:
Cuando un `ScrollView` necesite un espacio extra en la parte inferior para que el contenido no quede oculto por la navegación (ej. `paddingBottom: 100`), es OBLIGATORIO incluir `flexGrow: 1` en su `contentContainerStyle`. De lo contrario, el contenedor no se expandirá y los últimos elementos quedarán inaccesibles. Ejemplo correcto: `contentContainerStyle={{ flexGrow: 1, paddingBottom: 100 }}`.

A partir de ahora, revisa tu propio código antes de entregarlo para asegurarte de que no estás cometiendo ninguno de estos 3 errores.

# 🚨 DIRECTIVA DE LAYOUT: KEYBOARD-AWARE Y SCROLL EXCESIVO EN ANDROID

Para resolver problemas de márgenes vacíos y scroll excesivo en vistas detalladas y modales en React Native (Android), NO usar librerías externas de teclado como `KeyboardAwareFlatList` si causan padding fantasma (por propiedades como `extraHeight`). En su lugar, aplica este patrón nativo:

1. **Listas y Scroll Nativos:** Usar `FlatList` o `ScrollView` nativos.
2. **Restricción de Scroll:** Asegurar que tengan `contentContainerStyle={{ flexGrow: 1, paddingBottom: 32 }}`. Nunca permitir que un contenedor de teclado inyecte padding fantasma infinito.
3. **Contenedor Principal:** Envolver el contenido en un `KeyboardAvoidingView` con `behavior='padding'` para iOS y aplicar un **padding dinámico** basado en la altura del teclado para Android: `paddingBottom: Platform.OS === "android" ? keyboardHeight : 0`.
4. **SafeArea:** Usar `SafeAreaView` DENTRO del `KeyboardAvoidingView`.

Esto garantiza que el teclado no tape los inputs y elimina completamente el scroll vacío y las pantallas en blanco al final de las listas.

# 🚨 DIRECTIVA DE COMPILACIÓN TYPESCRIPT — OBLIGATORIA

La PC del usuario tiene RAM limitada. El comando `npx tsc --noEmit` consume demasiada memoria y congela el sistema.

## Reglas OBLIGATORIAS para verificar TypeScript:

### Frontend (puntodeventafront)
NUNCA usar: `npx tsc --noEmit`
SIEMPRE usar: `npm run typecheck`
→ Ejecuta: `node --max-old-space-size=4096 ./node_modules/typescript/bin/tsc --noEmit`
→ tsconfig tiene `incremental: true` y `skipLibCheck: true` para reducir RAM y tiempo
→ ⚠️ Si Expo está corriendo, el typecheck consume más RAM. 4 GB es el límite seguro con ambos activos.

### Backend (puntodeventabackend)
NUNCA usar: `npx tsc --noEmit`
SIEMPRE usar: `npm run typecheck`
→ Ejecuta: `node --max-old-space-size=2048 ./node_modules/typescript/bin/tsc --noEmit`
→ tsconfig ya tiene `incremental: true` y `skipLibCheck: true`

## Beneficios del modo incremental:
- Primera ejecución: crea caché `.tsbuildinfo` en el proyecto
- Ejecuciones siguientes: solo re-analiza los archivos que cambiaron (mucho más rápido y liviano)
- `skipLibCheck`: no re-verifica los tipos de `node_modules` (el mayor consumidor de RAM)
